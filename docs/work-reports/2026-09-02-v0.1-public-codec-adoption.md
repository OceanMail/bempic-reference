## Architecture and boundary decisions

- The active codec identity is the public experimental tuple
  `0x00010000/1`. Its allocation is experimental, not approved, not
  mandatory, and carries no stable-wire or production-security promise.
- Private tuple `0xffff0001/2` material may remain only as explicitly
  historical provenance and is excluded from active public conformance
  evidence.
- The pinned public profile supports the core-operation schema and the
  opaque-binary schema. It explicitly says that revision 1 does not support
  the message-manifest schema and defines no canonical manifest-instance byte
  encoding. Therefore this repository will not invent such bytes or label the
  existing pretty-JSON semantic fixture as a conforming manifest encoding.
  Public V01/V02 operation and opaque-representation evidence will be
  regenerated, while the mandatory rows remain blocked on the missing
  normative manifest encoding.
- Reserved IDs, private-use IDs, revision zero, unknown tuples, the allocated
  ID with an unsupported revision, non-empty parameters, and unsupported or
  mismatched schemas must be rejected before a negotiated profile or offered
  descriptor can mutate durable state.

## Unresolved blockers

- Public codec revision 1 defines no message-manifest instance encoding, so a
  conforming public-tuple manifest decoder and complete V01/V02 manifest
  vectors cannot be implemented without a specification decision. The
  smallest safe decision is a normative canonical manifest encoding with
  bounds, exact-size rules, malformed cases, and allocation/revision handling;
  because this changes accepted/emitted bytes and schema support, it likely
  requires a new codec revision.
- B2F remains blocked by the specification's
  `blocked-no-qualified-oracle` decision.
- M4P, independent implementation ownership, the security profile, and final
  release gates remain separate and unresolved.
